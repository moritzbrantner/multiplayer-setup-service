WebRTC rendezvous for browser multiplayer

Connect briefly. Play directly.

GitHub Pages serves the game. A small setup service introduces the players and relays WebRTC setup data. Once the peer links are ready, gameplay moves onto direct DataChannels whenever the network permits it.

Three phases

The server gets peers connected. It does not run the game.

The setup service is deliberately narrow: short-lived rooms and lobbies, private capabilities, authenticated WebSocket signaling, and targeted relay of opaque WebRTC setup messages.

Input-only synchronization

Send the decision, not the world.

For deterministic games, every player can run the simulation locally. The network carries compact sequenced inputs; each browser applies the same transition to its own copy of state.

01 · PlayerProduces a compact input command.
02 · WebRTCDelivers it to the peers required by the topology.
03 · Every deviceApplies the same deterministic calculation locally.
{
  "type": "step",
  "participantId": "7Q1M8X2K",
  "seq": 42,
  "dx": 1,
  "dy": 0
}

No position is authoritative here. The message says what the player did; the resulting position is calculated on every machine. Sequence numbers make duplicate and stale inputs fail closed.

ChannelSemanticsTypical data
ReliableOrdered delivery; retransmit until delivered.Moves, joins, scores, resets, inventory changes, turn-based commands.
RealtimeUnordered, zero retransmits; newest information wins.Frequent input/state hints where stale packets are less useful than fresh ones.

Ownership boundary

The setup service is infrastructure, not game authority.

Keeping this boundary narrow lets chess, Pong, physics games, card games, and future clients all reuse the same rendezvous service without coupling their rules to it.

Setup service owns

  • Short-lived rooms and 2–16 player lobbies
  • Participant identities and private capability authentication
  • WebSocket signaling connections and targeted relay
  • Expiry, capacity limits, reconnect replacement, and roster events

Peers / game own

  • Game rules, simulation, rendering, and local validation
  • Mesh versus host-spoke topology policy
  • Reliable versus freshness-first gameplay messages
  • Input sequencing, state hashes, reconciliation, and rollback as needed
